# MAGI V3 Supply-chain Contract

The immutable Python runtime tree remains hash-bound by the existing runtime
manifest. RC643 adds package-level evidence around that tree:

- an exact installed-distribution lock with METADATA and RECORD digests;
- a CycloneDX 1.5 SBOM generated by the bound runtime interpreter;
- a hashed offline wheelhouse manifest for runtime rebuild inputs;
- a vulnerability receipt bound to the exact package-lock digest and no older
  than seven days;
- a staged-release secret scan;
- a source policy that rejects new runtime package/browser installers.

Installer commands remain available only in explicit install/build workflows.
Sealed production services, legal portal workers and mutable skills fail closed
instead of contacting package indexes or downloading browser drivers.

## RC643 candidate boundary

- r59 runtime and release trees remain immutable rollback artifacts. Dependency repair is performed only in a separate candidate virtual environment.
- The RC643 security overlay is declared by `config/supply-chain/rc643-runtime-security-overlay.txt`; its wheels are downloaded before sealing, hash-manifested, and installed with network disabled.
- `mariadb`, `PyPDF2`, and `weasyprint` are absent from the candidate runtime. MAGI uses `mysql-connector-python`, `pypdf`, and the existing ReportLab PDF fallback respectively.
- Candidate acceptance requires `pip check`, a zero-known-vulnerability release-bound receipt, import smoke, source runtime-install audit, staged secret scan, runtime lock, SBOM and wheelhouse verification.
- A failed vulnerability scan may be retained as diagnostic evidence, but `validate_vulnerability_receipt` rejects every non-clean receipt. It can never certify a release.

RC643 uses an immutable base runtime plus a hash-bound offline security overlay.
`config/v3_supply_chain_binding.json` binds the r59 base runtime manifest and
tree, the candidate's final 289-package lock, CycloneDX SBOM, 25 overlay wheel
hashes and zero-known-vulnerability receipt. The release bundle CLI validates
this complete contract fail-closed before it can seal a formal release.

Files under `work/` remain development evidence and never authorize cutover.
Only the copies committed under `config/supply-chain/rc643-r64/`, their binding
manifest, the verified external base-runtime manifest and final sealed release
manifest form promotion evidence.

The `rc643-r64` directory name identifies the immutable dependency evidence set,
not permission to promote that source release. A later code-only RC643 candidate
may reuse the set only when the runtime tree, package lock, SBOM, wheelhouse and
vulnerability-receipt digests remain exact and the candidate bundle validates the
binding fail-closed. Any dependency drift requires a newly generated evidence set.
